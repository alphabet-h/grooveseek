# 19. frontmatter の key はすべて保持し、名指しは schema に任せる

- Status: accepted
- Date: 2026-09-09
- Deciders: プロジェクトオーナー
- Applies to: v1.9.0

## 背景と課題

`groove validate` は文書の frontmatter を `groove-schema.toml` に照らして検査する。本リリース
までは、schema が名指せる key は `title` / `date` / `topic` / `depth` / `tags` の 5 つだけで、
それ以外は名指せなかった。パーサが YAML ブロックをこの 5 つのフィールドを持つ struct へ
デシリアライズし、**serde の既定の挙動が、それ以外の key を下流の誰かが見る前にすべて
捨てていた**からである。`status` を名指す schema は読み込みの時点で拒否され、「schema が
名指していない key を指摘する」strict モードは存在し得なかった。バリデータは、そのブロックが
どの key を運んでいたかを一度も知らないからである。

74 文書のプラットフォームエンジニアリングのコーパスを運用しているユーザは、これをこう言い
表した (#252): ドメインのメタデータを持たないコーパスに strict モードは要らない。ドメインの
メタデータを持つコーパスは strict モードを使えない。その frontmatter は 21 種類の key を
運んでおり、そのうち宣言できたのは 5 つだった。報告者が提案したのは loader への 1 行の
変更 — `[fields.status] known = true` — で、schema が key を**検査せずに名指す**ための
ものである。

[ADR-0010](0010-settle-what-the-1-0-command-line-freezes.ja.md) は、受け取ってから捨てていた
`--strict` フラグを削除し、その復活の値段を付けた: `[options].allow_unknown_fields` がある
状態で足し直すなら、それは minor リリースである。

本決定が答える問い: **frontmatter にどの key が存在するかを決めるのは、パーサか schema か。**

## 判断の軸

- **loader の変更だけでは strict モードは成立しない。** 穴は 1 層下、パーサにある。どんな
  設計であれ `Frontmatter` が何であるかを変えることになり、それはすべてのパーサが構築し、
  索引を読む側すべてが触れる型である
- **frontmatter は最初から最後まで文字列として持つ。** `date` は schema が pattern で検査
  する文字列であり、`depth` も文字列である。schema が存在して以来これが規則であり、報告者
  もその変更は求めていない
- **宣言は必須化ではない。** 報告者の 21 の key のうち 11 は `source` に条件付けられている。
  key を名指すことが必須化を意味する schema にすれば、報告者が持つ全文書が指摘対象になる
- **パーサが保持する key は、YAML パーサが既に払った以上のコストを掛けてはならない。**
  未知の key の下の alias bomb や深い mapping は、以前と同じ入力である。保持することが
  それを歩いてはならない
- **検索索引・そのフィルタ・MCP ツールは凍結された面である** (`docs/stability.md`)。この
  コーパスが key を必要としている場所はバリデーションだけである

## 検討した選択肢

1. **rule の key としての `known = true`** (報告者の提案)。却下: 単体では成立しない。
   パーサが依然として key を捨てるからである。そしてパーサが key を保持するのなら値も保持
   してよく、その時点で `known` は「空のテーブル」を意味するだけのキーワードになる
2. **未知の値を YAML へ再シリアライズした文字列として保持する。** 形は 3 つではなく 2 つに
   なる。却下: `pattern` が YAML の構文に対して照合されることになり、mapping が
   `type = "string"` を通ってしまう
3. **名前付きの 5 フィールドをすべて 1 つの map に畳み、アクセサを付ける。** 一様になり、
   schema のディスパッチは 1 回の lookup になる。却下: 今日、すべてのパーサ・indexer・
   サーバとそれらのテストが 5 つのフィールドを名前で読んでおり、`tags` はその型が担保して
   いる `Vec<String>` の保証を失う
4. **5 つのフィールドはそのままに、3 つの形を持つ `extra: BTreeMap<String, FieldValue>` を
   足す。** 採用
5. **`type = "bool"` を足す。** 却下: `enum = ["true", "false"]` が既に表現している 1 つの形
   の表明のために、「最初から最後まで文字列」の規則を壊す。ドキュメントにそう書くことにし、
   読者に発見させるのをやめる
6. **タグの混在リストのために 2 つ目の正規表現 key を足す。** 却下: 1 フィールドにつき
   pattern は 1 つというのは rule の限界であり、報告者の軸タグと自由タグの整合はフィールドを
   またぐ制約で、報告者の外部バリデータが持つべきものである

## 決定

- **パーサはブロックのトップレベルの key をすべて保持する。** 自分のフィールドに格納する
  5 つは変わらない。それ以外の key はすべて、その名前のまま `Frontmatter.extra` へ入る。
  YAML の merge key `<<` だけが例外である: serde の flatten はこれを展開しないまま表に
  出してしまい、そもそもフィールドだったことはない
- **保持された値は 3 つの形のいずれかを取る。** 文字列・真偽値・数値は、それが印字される
  文字列である。要素がすべてそうしたスカラであるシーケンスは、文字列のリストである。それ
  以外 — mapping、そうしたスカラでないものを含むシーケンス、null、未解決の alias — は
  不透明であり、パーサは**形の名前**だけを保持して値を読まない。実際には、未知の key の下の
  alias はそれが指す値に解決された状態で届くので、不透明という場合は文書が通る経路という
  よりガードである。この分類は YAML の値型に対して**網羅的**であり、既定の arm を持たない。
  だから新しい形は、静かな 4 つ目の種類ではなくコンパイルエラーになる
- **schema はどの key でも名指せる。** `[fields.<name>]` はどんな名前も受け取る。空の
  テーブルは key を宣言し、何も検査しない。`required = true` は明示のままである。既存の
  rule は、`type` が与えられていなければ保持された値の形に従って、与えられていればその
  `type` に対して適用される。不透明な値は `required` を満たし、それを読もうとする rule に
  対しては自分の形を名指す `type_mismatch` を 1 件報告する
- **`[options].allow_unknown_fields = false`、または `groove validate --strict` は、schema が
  名指していない key を 1 件ずつ `undeclared_field` 違反として key 順に報告する**。名前付きの
  5 フィールドは常に宣言済みである。パーサが拒否したブロックは、これまで通り
  `frontmatter_unparsed` 1 件だけで、それ以外は何も出ない。フラグは**締める方向にしか
  働かない**: `--no-strict` は無い
- **保持された key が届く先は、本リリースでは `groove validate` だけである。** schema が宣言
  した key を `search` / `graph` / MCP ツールで**フィルタできるようにする**ことは、意図された
  次の一歩であって、この記録が閉じる扉ではない (#289 は、その意図をどちらにせよ書き残す
  ことを求めた)。それが別の決定なのは、索引と、凍結された結果およびフィルタの面に触れ、
  それぞれに自分の値段があるからである。この記録が決めるのは、**パーサが何を保持し、
  バリデーションがそれで何をするか**だけである

## 結果と代償

- **`groove validate --strict` が再び parse される。** 1.0.0 で ADR-0010 が外し、1.9.0 で
  その ADR が予約していた意味を伴って戻る。`[index].fail_on_frontmatter_error` は自分の
  意味のために自分の名前を保つ
- **`Frontmatter` にフィールドが 1 つ増えた。** Markdown 以外のパーサはこれを空のままに
  する。全フィールドを名指して `Frontmatter` を構築しているコードは、このフィールドも
  名指す必要がある
- **1.8.0 のバイナリが `unsupported field` で拒否していた schema が、1.9.0 では読み込める。**
  `type` の無い `[fields.tags] pattern` を持つ schema は 1.8.0 で報告を始めた。それ以外に、
  以前読み込めていたもので報告内容が変わるものは無い。既定の `allow_unknown_fields = true`
  が 1.8.0 の挙動そのものだからである
- **`serde` の flatten は struct 全体をバッファリングする経路へ移す。** テストで固定した
  ことが 2 つある: 形の合わない名前付きフィールド (`topic: [a]`) が今も拒否されること、
  および `title` に数値を与えたときに従来どおり文字列 `"123"` へ強制されること。どちらも
  以前のテストは覆っていなかった
